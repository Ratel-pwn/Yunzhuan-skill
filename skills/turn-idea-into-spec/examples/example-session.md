# 示例对话：把“想法”变成“可开发的设计文档”

> 目的：展示本 Skill 如何从“模糊想法”推进到“可开工文档 + 交付计划”。

---

## 用户

我想做一个功能：给我们的 B2B SaaS 加一个“邀请成员加入团队”的能力。希望你以 PM/TM 的方式帮我验证下方案，并输出完整的设计文档，开发照着做就行。

## AI（阶段 1：澄清与定界）

我会按 PM/TM 的方式推进：先定边界与成功标准，再出可开发的设计文档（默认单文件 `design-doc.md`）。我先确认 7 件事：

1) 一句话目标（用户价值 + 业务价值）是什么？  
2) 目标用户/场景：谁会发邀请、谁会接受？  
3) 成功指标：上线后看什么算成功？（激活率/邀请转化/留存等）  
4) 约束：截止时间、人力、平台（Web/移动端）、合规/安全要求？  
5) MVP 范围：这期 Must / Should / Could 分别是什么？  
6) 现状与集成：已有“团队/成员/权限”系统吗？有没有 SSO？  
7) 最大未知与风险 Top 3 是什么？

你可以先用一句话回答每条；如果有不确定的，我会给默认并让你确认。

## 用户

（略）

## AI（阶段 3：产出设计文档 v1）

收到。我将输出一份 `design-doc.md`，包含：

- PRD：目标/范围/需求与验收（AC）
- 技术设计：方案权衡、数据模型、API、权限、幂等、错误码
- 落地计划：里程碑、Backlog、测试/灰度/回滚、监控告警

我会把不确定的点标注为“假设/待确认”，并集中到 Open Questions。

（随后输出完整 Markdown 设计文档…）

## AI（质量自检）

我做一次交付前自检，并把缺口列出来让你确认：

1. P0 需求是否都有可测试的 AC？  
2. 邀请链接/邮件是否需要签名与过期？过期后行为是什么？  
3. 邀请与成员关系的幂等：同一邮箱多次邀请如何处理？  
4. 权限模型：谁能邀请/撤销/重新发送？审计日志要不要？  
5. 灰度与回滚：是否需要开关/白名单？监控指标是什么？

确认完这些点，我会更新文档到 v1.1。
